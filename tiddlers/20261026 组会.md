## macos LPE

### 结论

在 macOS 27.2 build 26B118 上，一个不属于 admin 组的标准本地用户可以自行挂载 autofs，并把自己拥有的可执行文件注册为 map。访问该挂载点中的 key 后，root automountd 会 fork 子进程，并在没有降权的情况下执行这个用户文件。

测试中，map 子进程以 uid=0(root) 运行并创建了 root-owned marker；Target Flag 模式还让这个 UID 0 子进程跳转到 Commpage 给出的目标地址，崩溃日志中的 PC/FAR 与该地址一致。

autofs 的信任边界出了什么问题

autofs 的 map 用来告诉系统：访问某个 key 时应返回怎样的挂载配置。map 不一定只是静态文本；当 map 文件带有可执行位时，automountd 会把它当作程序运行，并从程序的标准输出读取结果。

单独看这个设计并不等于漏洞。问题出在两个原本不应组合在一起的行为：

标准用户可以调用公开的 mount("autofs", ...)，把自己控制的路径作为 map 注册进去；

root automountd 接到 lookup 请求后，会执行这个 map，但子进程没有降回发起挂载的用户身份。

最终链条可以压缩成下面这样：

```
标准用户
  │
  ├─ mount("autofs", user_mountpoint, ..., map=user_owned_file)
  │
  └─ stat(user_mountpoint/directkey)
          │
          ▼
     autofs lookup request
          │
          ▼
     root automountd
          │ fork + execv(user_owned_file, [file, "directkey"])
          ▼
     攻击者控制的 map 子进程，uid=0
```

### 同源策略与 CORS 的关系

Origin 是以下三项的组合：

scheme + host + port

例如：

1. https://attacker.127-0-0-1.dev:22645
2. https://victim.127-0-0-1.dev:22643


它们不同源，因为 hostname 和 port 不同。

同源策略默认禁止 attacker 页面读取 victim 的响应。CORS 是 victim 主动放宽该限制的机制。例如：

```
Access-Control-Allow-Origin: https://attacker.example
Access-Control-Allow-Credentials: true
```

没有这些响应头，攻击者 JavaScript 就不应读取响应。

### CORS 有两道不同的检查

#### 第一道：响应检查

对普通 GET，例如：

```
fetch(victim + "/token", {
    mode: "cors",
    credentials: "include"
})
```

这种请求通常可以直接发送。浏览器收到响应后检查：

```
Access-Control-Allow-Origin
Access-Control-Allow-Credentials
```

PoC 的 victim 故意不返回这些头。正常结果应是：

请求可能到达 victim
Cookie 可能被发送
JavaScript 不能读取响应

因此，CORS 不是阻止所有网络请求，而是控制响应能否交给发起请求的跨源页面。

Safari 的漏洞破坏了这道检查：/token 的 JSON 响应被直接交给攻击者脚本。


#### 第二道：预检

当请求包含非 safelisted 内容时，浏览器需要先询问 victim。

PoC 使用：
```
fetch(victim + "/mutate", {
    mode: "cors",
    credentials: "include",
    headers: {
        "X-CSRF-Token": token
    }
})
```

X-CSRF-Token 不是 safelisted 请求头，因此正常浏览器必须先发送：
```
OPTIONS /mutate
Origin: https://attacker.127-0-0-1.dev:22645
Access-Control-Request-Method: GET
Access-Control-Request-Headers: x-csrf-token
```

只有 victim 返回类似下面的授权后，浏览器才能继续：
```
Access-Control-Allow-Origin: https://attacker.127-0-0-1.dev:22645
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: X-CSRF-Token
```

PoC 的 victim 没有返回这些授权，所以正常路径不会发送真正的 GET /mutate。

Safari race 路径绕过了这道检查，直接发出了：

```
GET /mutate
Cookie: victimAuth=AUTH_51E7
X-CSRF-Token: CSRF_TOKEN_51E7
```

为什么 attacker 看不到 Cookie，却可以利用登录状态
victim 设置的是：
Set-Cookie: victimAuth=AUTH_51E7; Path=/; HttpOnly; Secure; SameSite=Lax
它有三个关键属性：
- HttpOnly：攻击者 JavaScript 无法通过 document.cookie 读取。
- host-only：只会发送给 victim.127-0-0-1.dev。
- SameSite=Lax：在这个 same-site、cross-origin 测试拓扑里允许浏览器把它发给 victim。


因此攻击者看到的不是 Cookie，而是浏览器使用 Cookie 后得到的认证响应：

```
{
  "authenticated": true,
  "csrfToken": "CSRF_TOKEN_51E7",
  "counter": 0
}
```


这也是该 PoC 的安全意义：它证明了攻击者可以利用受害者现有会话读取受保护数据，并完成经过 token 验证的状态修改。

### Race

```
                    ┌─ 路径 A：Network preload  （win）
fetch /token ───────┤
                    └─ 路径 B：Service Worker fetch handler
```

#### /token 和 /mutate 各发生一次 race

第一次 race：

```
fetch /token
├─ Network preload → victim JSON，Safari 中获胜
└─ Fetch handler   → 500ms 后返回 fallback
```

攻击者因此得到 CSRF token。

第二次 race：

```
fetch /mutate + X-CSRF-Token
├─ Network preload → 直接发送 GET，没有 OPTIONS，Safari 中获胜
└─ Fetch handler   → 500ms 后返回 fallback
victim 收到 Cookie 和 token，把 counter 从 0 改成 1。
```


所以完整攻击链中实际进行了两次独立的 race：

第一次 race：绕过响应 CORS，读取 token
第二次 race：绕过预检，完成状态修改
